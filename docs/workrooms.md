# Workrooms

The private place a client is given for one piece of work. Introduced in
Build 004, the first client-facing build.

Written before the schema and reviewed against the situations at the end of
this file before a migration was generated. Where a rule here is marked
**invariant**, PostgreSQL enforces it.

Client identity and sessions are in [`client-auth.md`](./client-auth.md); the
client-facing timeline is in [`activity.md`](./activity.md); the business
records underneath are in [`business-core.md`](./business-core.md).

---

## What a Workroom is, and is not

| | Is | Is not |
| --- | --- | --- |
| **Workroom** | The curated, client-facing container around **one Project**. | The Project. The Project stays the internal record of the work. |
| | A place with its own client-safe title and summary. | A view of the Project's internal fields. |
| | Access, granted per person. | A door that opens because somebody works at the Client. |

**The Workroom is not the Project.** That separation is the whole design: it is
what lets internal notes, statuses and history stay internal while a client sees
something written for them.

```
CLIENT ──▶ PROJECT ──▶ WORKROOM ──▶ MEMBERSHIP ──▶ CONTACT ──▶ CLIENT IDENTITY
                           │
                           └──▶ ACTIVITY   (client-safe timeline)
```

---

## One Workroom per Project

**Invariant:** `workrooms.project_id` is `UNIQUE`. A Project has at most one
Workroom, decided by the database rather than by a read that two simultaneous
"Create workroom" presses could both pass.

**There is no `client_id` on a Workroom.** It would be a second copy of
`projects.client_id` and could drift from it, and the whole point of the
business core is that one fact lives in one place. The Client is reached by
joining through the Project, which is also the only relationship that can never
change — `updateProject` cannot move work to a different client, by design.

---

## The opaque identifier

A Workroom's URL uses `public_id`: 26 characters of Crockford base32 over 16
random bytes, generated by `lib/workrooms/id.ts`.

It is **not** the row's UUIDv7, because a UUIDv7 carries its creation timestamp
in the first 48 bits. A client-facing URL should not say when a piece of work
began, and it should certainly not say whose it is:

```
yiddiweller.com/workrooms/8f3kq2m7rv0x1ndyt4cbwzp6ha
```

No project name, no client name, no business name, no timestamp, no sequence.

**The identifier is not authorization.** It is unguessable so that a link cannot
be found by accident; every read behind it still checks membership server-side,
and an unguessable URL with no check would be a secret shared by anybody it was
ever forwarded to.

## Lifecycle

Four states, from a `status` of `draft | published | unpublished` plus the
`archived_at` every business record already has.

| State | Staff | Client |
| --- | --- | --- |
| **Draft** | Configure it, preview it. | Cannot reach it. Not listed. |
| **Published** | Everything. | Members can open it. |
| **Unpublished** | Everything. | Cannot reach it. Nothing is destroyed. |
| **Archived** | Read it, restore it. | Cannot reach it. |

**Publishing is deliberate.** Creating a Workroom does not expose anything: a
new one is a Draft, and somebody has to look at what the client will see and
choose to publish it. Both the publish and the unpublish are audited.

**Lifecycle is not tied to Project status.** A Project reaching `completed` does
not close the Workroom, because the moment work finishes is exactly when a
client goes back to look at it — and from Build 005 that is where their files
will be. Closing access is a separate, deliberate act.

## Membership is explicit

Being a Contact **at** the Client does not grant access. Being attached **to**
the Project does not grant access. Access is one row, per person, per Workroom.

Without that rule, one relationship row would quietly give somebody every
Project their company has ever commissioned.

- **Invariant:** `UNIQUE (workroom_id, contact_id)` — one membership row per
  person per Workroom, whose `status` is `active` or `revoked`.
- Revoking flips the status; it never deletes the row, and the audit log keeps
  the full history of who granted and revoked what, and when.
- Re-inviting a revoked person reactivates that same row rather than creating a
  second one, so "have they ever had access" has one answer.

**Revocation is immediate**, because access is checked on every request against
the row rather than trusted from the session. Revoking Workroom A does not touch
the person's access to Workroom B, and does not sign them out.

There are no member roles. A client is an authorized participant. Reviewer,
Approver and the rest are Build 005's problem, if Build 005 actually needs them.

## Who can be invited

Staff invite an existing canonical **Contact** — never a typed email address.
Build 003 owns who a person is; Build 004 owns what they can reach, and blurring
the two is how a CRM ends up with a second, shadow list of people.

An invitable Contact:

- is not archived,
- has an email address,
- and is already related to the Workroom's **Client** or its **Project**.

If the person is not there yet, staff create the Contact and the relationship
first. That is one extra step, deliberately: it means the business record exists
before the access does.

A Contact with no email cannot be invited, and the interface says so rather than
inventing a placeholder address.

## Invitations

| | |
| --- | --- |
| Token | 32 random bytes, hex. Only its SHA-256 digest is stored. |
| Scope | One Workroom, one Contact. |
| Life | Seven days. |
| Use | Once. |
| Revoke | Any time, by staff. |
| Resend | Revokes the old one and issues a new one, in one transaction. |

- **Invariant:** at most one *open* invitation per Workroom and Contact, a
  partial unique index over `WHERE accepted_at IS NULL AND revoked_at IS NULL`.
  Two people pressing "Invite" at the same moment produce one invitation.

**A GET never consumes an invitation.** Mail security scanners and link
previewers open URLs before a person does, and an invitation that burned itself
on the scanner's request would lock the client out before they ever saw it. So
the link renders a confirmation page, and a POST — a deliberate press — accepts.

Acceptance is one transaction: claim the invitation, create or reuse the client
identity, grant the membership, write the audit event and the client-safe
activity. Any failure rolls all of it back. Only then is the session issued.

## What the client sees

**A whitelist, never a hidden field.** Nothing reaches a client surface except
through `toClientWorkroomView` in `lib/workrooms/view.ts`, which names every
field explicitly. A database row is never spread into a client component.

Visible:

- the Workroom's own `title` and `summary`, written for the client
- the Project's **status**, as a word
- `starts_on` and `target_on`
- the Client's name
- the other people **in this Workroom**
- the Workroom's Activity

Never visible, and not fetched at all on a client request:

- `clients.notes`, `contacts.notes`, `projects.notes`, `projects.description`
- anything at all about Leads, including summaries and lost reasons
- `audit_events`
- other Workrooms, other Projects, other Clients, other Contacts
- internal ids beyond the Workroom's own `public_id`
- who internally changed anything

`projects.description` is deliberately **not** shown. It is an internal field
written for the studio, and "it is probably fine" is not a privacy model. The
Workroom's `summary` is the field written for the client, and staff can see
exactly what that produces before publishing.

## Preview

Staff can see the client view from inside Studio, rendered through the same
`toClientWorkroomView` projection so it cannot drift from what a client gets.

It is a staff-authorized Studio route. It does **not** issue a client session,
does not impersonate anybody, and creates no URL a client could discover. There
is no "log in as this client" feature and there will not be one.

## Archive and lifecycle guards

Build 003's guards still hold, and Build 004 adds its own. Each refusal names
what is blocking it.

| Attempt | Result |
| --- | --- |
| Archive a Project whose Workroom is published | **Refused.** Unpublish the Workroom first — archiving work a client can still open is an incoherent state. |
| Archive a Contact with active Workroom membership | **Refused**, naming the Workrooms. Revoke the access first. |
| Archive a Client with live Projects | **Refused**, as in Build 003. |
| Publish an archived Workroom | **Refused.** |
| Publish a Workroom whose Project is archived | **Refused.** |
| Archive a published Workroom | **Refused.** Unpublish it first, so losing client access is never a side effect. |

Nothing here is ever hard-deleted.

## Who may manage a Workroom

| | Owner | Member |
| --- | --- | --- |
| Create and configure a Workroom | ✓ | ✓ |
| Preview | ✓ | ✓ |
| Publish, unpublish | ✓ | ✓ |
| Invite, resend, revoke an invitation | ✓ | ✓ |
| Grant and revoke membership | ✓ | ✓ |
| **Archive and restore a Workroom** | ✓ | — |
| **Disable or re-enable a client identity** | ✓ | — |

Running a client's project is ordinary work, so a Member does it. The two
Owner-only actions are the ones that reach beyond a single Workroom: archiving,
and switching off a person's identity everywhere at once.

## Reviewed against real situations

| Situation | How the model holds it |
| --- | --- |
| **Organization client, one project** | One Workroom, memberships for the people who should see it — not everybody at the company. |
| **Individual client** | Identical. The Client is the account, the Contact is the person, and they are linked as in Build 003. |
| **Several people at one client** | Several memberships on one Workroom. |
| **A contact who acts for two clients** | One Contact, one client identity, memberships in Workrooms under both. They sign in once. |
| **One client, several projects** | Several Workrooms. The index lists only the ones they are a member of. |
| **An existing identity gets another invite** | The identity is reused and only a membership is added. Never a second account. |
| **Somebody's contact email changes** | Their *access* email does not. See [`client-auth.md`](./client-auth.md). |
| **Access revoked** | The membership flips to `revoked`, immediately. Other Workrooms are unaffected. |
| **Identity disabled** | No new session, and existing sessions stop working everywhere. |
| **Archived Contact** | Cannot happen while they hold active access — the archive is refused, naming the Workrooms. |
| **Archived Project** | Refused while its Workroom is published. |
| **Completed project, client still needs access** | Nothing closes. Project status is a word on the overview; access is a separate decision. |
| **Build 005 files** | Attach to `workrooms.id`. Membership already answers "may this person see it". |
| **Build 005 approvals** | A membership row is already the place a capability would hang, if one is ever needed. |
| **Build 006 billing** | References `clients.id` and `projects.id`, as Build 003 locked. Nothing financial is squatting here. |
| **Build 007 communications** | References `contacts.id` and `workrooms.id`. Activity stays a system timeline and does not become a message list. |
