# Activity

What has happened in a client's Workroom, written for the client.

Introduced in Build 004. The distinction it depends on — Activity is not Audit —
was recorded in [`audit.md`](./audit.md) in Build 003, before either existed as
a table, so that the two could not be conflated once they did.

---

## Three things, permanently separate

| | **Audit** | **Activity** | **Communications** — Build 007 |
| --- | --- | --- | --- |
| Answers | Who changed what, when? | What has happened in my Workroom? | What did we say to each other? |
| Written for | Accountability | The client | Both sides of a conversation |
| Read by | Owners, rarely | Workroom members, and staff | Whoever is in the thread |
| Mutable | **Never.** PostgreSQL refuses `UPDATE`, `DELETE` and `TRUNCATE`. | Append-only by design; retention is a product decision. | Threaded, editable by product rules |
| Contains | Ids, vocabulary, field names | Safe labels only | Messages people wrote |
| Table | `audit_events` | `workroom_activity` | not built |

Merged, they produce either a client-facing feed full of security noise, or an
audit trail somebody can edit, or a timeline that is neither. Each of the three
is written once, into its own table, by the code that causes the event.

**Activity is never generated by rendering Audit.** They are written
independently in the same transaction, from the same business event, with
different content. Neither reads the other as its storage.

---

## Safe by construction, not by redaction

The strongest guarantee this design can offer is structural, so it takes it:

# There is nowhere in `workroom_activity` to put a note.

A row has four pieces of content and no free-form blob:

| Column | Holds |
| --- | --- |
| `kind` | One value from a fixed vocabulary, `CHECK`-constrained. |
| `actor_label` | A person's name, or null. A snapshot. |
| `subject` | One safe word or short label — a status, a Workroom title. |
| `occurred_at` | When. |

There is no `metadata`, no `detail`, no `body`. Nothing can be pasted in by
accident, because there is no column to paste it into. A future event that
genuinely needs more will have to add a named column and argue for it in review,
which is exactly the friction this deserves.

Compare `audit_events`, which does have a `metadata` jsonb — because audit is
internal and its policy is enforced by review. Activity is read by people
outside the company, so its policy is enforced by the schema.

## The vocabulary

Build 004 writes five kinds:

| `kind` | Reads as | Written when |
| --- | --- | --- |
| `workroom.opened` | *Workroom opened* | Published for the first time. |
| `workroom.joined` | *Nora Wind joined* | An invitation is accepted. |
| `workroom.access_granted` | *Sam Fox was given access* | A revoked membership is restored. |
| `workroom.access_ended` | *Sam Fox's access ended* | A membership is revoked. |
| `project.status_changed` | *Status changed to Active* | A Project with a live Workroom changes status. |

Build 005 adds seven, specified in [`delivery.md`](./delivery.md) and **not
written until Build 005 is built** — there is no placeholder for them:

| `kind` | Reads as |
| --- | --- |
| `file.shared` | *Brand guidelines was shared* |
| `presentation.published` | *Identity concepts is ready* |
| `presentation.revised` | *Identity concepts was updated* |
| `review.requested` | *Your thoughts were requested on Identity concepts* |
| `review.received` | *Ana Alder sent feedback* |
| `approval.requested` | *Approval was requested for Identity concepts* |
| `approval.decided` | *Ana Alder approved Identity concepts* |

`subject` carries a File's `display_name` or a Presentation's `title` — both
already client-facing fields, never internal ones. **`approval.decided` is one
kind, not two**: the verb comes from the approval record, and a decline is not a
separate species of event.

**`presentation.viewed` is deliberately absent.** `architecture.md` once gave it
as an example of business activity. It is not built, here or in `audit_events`:
this table is the *client's* timeline, so a row saying they opened something
shows a client a log of their own reading. That is surveillance in a product
whose principle is *personal everywhere*, and the decision is recorded so nobody
later reads the old example as an intention.

**Twenty files shared at once is twenty rows.** Collapse consecutive same-kind
events **in the reader** — *"6 files were shared"* — while the table keeps one
row per file and stays honest. Collapse in the projection, never in the table.

Build 007 may add communication events.

**`project.status_changed` carries the status and nothing else.** Not who inside
the studio changed it, not why, not the note they wrote next to it. The internal
half of that same business event goes to `audit_events`, with the actor and the
field names, where only an Owner reads it.

## Actor labels are snapshots

`actor_label` stores the name as it was when the event happened, the same
reasoning as `audit_events.actor_name`: a timeline that rewrites itself when
somebody changes their name stops being a record of what happened.

Live identity is used for everything that describes the present — the People
section names people from their canonical Contact — and the snapshot is used
only for history. Both, deliberately, in the places each is right.

A staff-caused event is labelled with the studio's name rather than an
individual's unless naming the person is the point. A client does not need, and
should not receive, the internal shape of who does what inside the company.

## Append, and what to do when something was wrong

Activity is history: the interface has no edit and no delete, and
`lib/db/activity.ts` exposes `record()` and readers and nothing else.

When a later business change contradicts an earlier event, the answer is another
event, not a correction. *Status changed to On hold* followed by *Status changed
to Active* is the truth; editing the first one into the second is not.

It is not trigger-locked the way `audit_events` is, and that is a deliberate
difference rather than an oversight. Audit answers to compliance and must be
immutable even against a console. Activity is client-facing product content
whose retention is a product decision — the same distinction the table at the
top of this file draws. If that ever changes, the triggers are three lines and
`0002_business_core.sql` shows how.

## Reading it

A client sees their Workroom's Activity, newest first, on the Workroom page.
Staff see the same rows in Studio, through the same reader, under a heading that
says what it is: **what the client can see**.

Timestamps use Build 002's date system — UTC in the database, the reader's own
zone in the browser, through `<Moment>`. A client in Brussels and a client in
New York see the same instant written in their own time, and neither sees the
server's.
